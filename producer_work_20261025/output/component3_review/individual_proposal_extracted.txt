ABSTRACT 
 
Modbus/TCP is still popular in industrial controls and supervisory applications but does not offer some 
of the built-in integrity and/or authentication protections found in other primary protocols. This allows 
an opponent to send a valid command or a spoofed reply that might look like a typical command or 
reply if seen in isolation. Intrusion detection has been studied by existing systems using signatures, 
generic flow statistics, individual protocol fields, or sequence analysis, individually. Very few works 
combine the reconstructed request-response relationships with operational context, in an explainable 
model, to differentiate between normal traffic, command injection and response injection. 
The purpose of this research is to propose a Modbus/TCP context-aware detection component. It 
makes ordered traffic into request-response events and engineers' protocol-semantic features to 
describe function-code transitions, read/write ordering, register-access behavior, timing, response 
consistency, source-role behavior (where available) and value transitions. Each contextual event will 
then be classified as normal, command injection or response injection using a supervised Random 
Forest classifier. The main experiment will compare the context-aware Random Forest with an 
algorithm trained only on isolated packet/static features to measure the contribution of context without 
being intertwined with the classifier. XGBoost can be taken as an additional benchmark. 
The development of the models will be primarily based on the CICModbusDataset2023, which 
contains benign and attack Modbus/TCP PCAP captures with attack logs and timestamps. Time, target 
IP, attack scenario and transaction identifier (if available) will be used to correlate packet records with 
the logs. Then the direction and request-response relationships will be checked to verify them, prior to 
candidate false-data-injection events being mapped to command or response injection. Secondary 
validation will be provided by the MSU New Gas Pipeline dataset that explicitly includes command- 
and response-injection categories. There will be no leakage in the data by splitting them by scenarios, 
capture, or time. Macro precision, macro recall, macro F1 score, false positive rate, ROC-AUC, 
confusion matrix, detection latency, and per-class recall will be used to assess performance.

1. INTRODUCTION 
1.1 Background and Context 
 
Industrial Control Systems (ICS) are computer-based systems that monitor and control critical 
infrastructure and industrial processes. They are used in power generation and distribution, water and 
wastewater treatment, oil and gas pipelines, food processing, and manufacturing. These environments 
contain supervisory applications, Human-Machine Interfaces (HMIs), Programmable Logic Controllers 
(PLCs), Remote Terminal Units (RTUs), sensors, and actuators that exchange operational commands 
and measurements. 
Modbus is one of the communication protocols used within these environments. Modbus/TCP enables 
Modbus communication over TCP/IP networks and supports operations such as reading measurements, 
controlling coils, and modifying register values. However, Modbus was originally designed for simple 
and reliable industrial communication rather than modern cybersecurity requirements. It does not 
provide strong native authentication, encryption, or cryptographic message-integrity protection [1], [2]. 
Consequently, a receiving device may be unable to verify whether a message originated from an 
authorized source or was modified during transmission. 
Historically, many industrial networks were physically isolated from conventional information-
technology networks. Modern industrial organizations increasingly require remote monitoring, 
centralized administration, data sharing, and integration between IT and OT environments. Although 
this connectivity improves operational efficiency, it also increases the possible paths through which an 
attacker may reach industrial devices [2], [4], [11]. 
Attackers can exploit Modbus/TCP environments in several ways. A denial-of-service attack may 
overwhelm a system with excessive traffic and affect availability. Reconnaissance may be used to 
identify active devices, accessible addresses, and supported operations. Command injection inserts an 
unauthorized or falsified control request, while response injection creates or modifies a reply to 
misrepresent the state or result of an operation [6]. A replay attack captures a previously valid 
transaction and retransmits it later. 
The complete group solution therefore consists of a protocol-aware detection framework with four 
specialized components: 
• Denial-of-service detection 
• Reconnaissance detection 
• Command and response injection detection 
• Replay-attack detection 
These components examine different attack behaviors and send their results to a shared decision-fusion 
and incident-analysis layer. The integrated framework then produces correlated alerts, confidence 
information, and incident explanations. 
The proposed Command and Response Injection Detection component focuses specifically on 
malicious commands and responses that may appear structurally valid. An injected message may 
contain an accepted function code, correctly formatted fields, and a legitimate-looking register address 
while still being operationally inappropriate. For example, a valid write command may be issued by an 

=== PAGE 14 ===
 
Page 14 
unexpected source, target a restricted register, produce an unusual value change, or conflict with the 
preceding command sequence. 
Existing security approaches often depend on fixed rules, protocol-validity checks, isolated-packet 
inspection, or general network-flow measurements. These methods can detect known signatures, 
malformed messages, and high-volume anomalies. However, they may not sufficiently represent 
Modbus command meaning, request-response relationships, source roles, register-access behavior, or 
surrounding operational context [3], [6], [8]. As a result, a protocol-valid command or response may 
remain undetected when its abnormality becomes visible only through contextual analysis. 
The proposed component addresses this problem by reconstructing Modbus request-response events 
and engineering contextual features from command order, access permissions, timing, pair 
consistency, source behavior, and value transitions. A supervised Random Forest classifier then uses 
these features to classify events as normal, command injection, or response injection. The component 
also produces a confidence score and explanatory evidence for integration with the complete 
framework. 
This research primarily supports United Nations Sustainable Development Goal 9-Industry, Innovation 
and Infrastructure-by contributing to the security and resilience of industrial infrastructure. It also has a 
secondary relationship with Sustainable Development Goal 7-Affordable and Clean Energy-because 
Modbus/TCP is used in energy and utility environments. The project aligns with the AIMS research 
group and the Cybersecurity and Information Assurance research cluster. It also relates to Artificial 
Intelligence and Machine Learning using machine-learning models across the integrated detection 
framework. 
 
1.2  Research Problem 
Modbus/TCP command and response injection attacks are difficult to detect because malicious 
messages may follow the correct protocol format and contain valid function codes, register addresses 
and transaction information. Although such messages appear legitimate when analyzed individually, 
they may be abnormal when compared with the communicating device’s role, previous commands, 
permitted register access, expected values or corresponding request and response. 
Existing packet-level and generic flow-based detection approaches may not represent these contextual 
relationships sufficiently. This creates the risk that an unauthorized command or falsified response will 
be treated as normal communication. Therefore, this research investigates how Modbus/TCP request 
response relationships and surrounding command context can be represented as structured features and 
analyzed using supervised machine learning. 
 
1.2.1 Problem Scope and Boundaries 
The proposed component focuses on low-volume manipulations that change the meaning or outcome 
of Modbus/TCP communication rather than attacks that mainly increase traffic volume. A command-
injection event may introduce an unauthorized state change, abnormal parameter value, unexpected

write operation, prohibited register access or inappropriate use of a valid function code. A response-
injection event may fabricate or alter the reply received by a supervisory application. 
The component determines whether each event is consistent with the communicating device’s role,

request or response and expected value transitions. It classifies supported events as normal, command 
injection or response injection. 
Query flooding, ping flooding, TCP SYN flooding and other availability-oriented attacks are outside

The proposed component may use a Modbus transaction identifier to associate a request with its 
corresponding response. However, it does not detect replay attacks. RP4 is responsible for transaction-

1.3 Literature review 
 
1.3.1 Modbus/TCP Security and Command Injection 
Modbus/TCP exchanges commands and process measurements among HMIs, SCADA servers, PLCs, 
sensors and actuators. Standard Modbus/TCP was designed for dependable industrial communication 
and does not natively provide strong authentication, confidentiality or cryptographic message-integrity 
protection [1], [2]. Consequently, an attacker with network access may transmit a correctly structured 
but operationally illegitimate message. 
Command injection inserts or modifies a request, such as an unauthorized register-write operation. 
Response injection fabricates or alters a reply so that the supervisory application receives incorrect 
information. Because these messages may use valid function codes, addresses and packet structures, 
detection should consider their relationship with previous commands, device roles, permitted register 
access and the corresponding request or response. 
 
1.3.2 Command and Response Injection Detection 
Gao et al. investigated command and response injection in an experimental SCADA environment and 
distinguished manipulation of control requests from manipulation of response information [6]. The 
study demonstrated that protocol and process information can support detection and established the 
two attacks as separate categories. However, it predates recent Modbus datasets and explainable 
machine-learning workflows. It did not fully evaluate whether request-response relationships, 
command history, permissions and value transitions could form a reusable contextual representation. 
This work supports the proposed three-class formulation - normal, command injection and response 
injection and motivates reconstructing request-response events before classification.

1.3.3 Model-Based Modbus/TCP Intrusion Detection 
Goldenberg and Wool developed a deterministic model of expected Modbus/TCP behavior for 
individual HMI–PLC channels [3]. It represented function codes, addresses, message lengths and 
communication sequences. On production traffic, the authors reported no false alarms for five of seven 
PLCs for 111 hours and detected genuine operational anomalies [3]. 
The approach demonstrates the value of protocol-specific behavior and command order. However, 
exact behavioral models may depend heavily on previously observed patterns. Legitimate operational 
changes can generate alerts, while an attacker may reuse a permitted operation in a harmful context. 
The method also does not separately classify command and response injection. The proposed 
component therefore preserves sequence information but uses Random Forest to learn combinations of 
command, access, timing, pairing and value evidence. 
 
1.3.4 Machine Learning for Malicious SCADA Communication 
Beaver, Borges-Hink and Buckner compared supervised machine-learning classifiers using labelled 
SCADA network and protocol attributes [8]. Their findings support supervised classification when 
suitable labelled features are available. A key strength is the comparative evaluation of multiple 
algorithms on structured industrial-control data. 
However, the study focused on broader malicious-communication detection rather than separating 
command injection from response injection. Individual records may also omit what happened before an 
event or whether a response agrees with its request. The proposed research retains supervised 
classification but adds previous-command, request-response, register-access and value-change context. 
 
1.3.5 Industrial-Control Traffic Datasets  
Morris and Gao introduced industrial-control traffic datasets for intrusion-detection research [5]. The 
MSU New Gas Pipeline dataset contains explicit normal and attack labels. For this research, normal 
records remain normal; naïve and complex malicious response injections are mapped to response 
injection; and malicious state, parameter and function-code injection are mapped to command 
injection. Denial-of-service and reconnaissance records are excluded from component training. 
The dataset provides explicit injection categories, but it is simulated, relatively old and lacks complete 
transaction information in some structured records. It therefore cannot support every request–response 
feature and is used mainly for secondary or external validation with a reduced common feature set. 
 
1.3.6 CICModbusDataset2023 
CICModbusDataset2023 provides benign and attack Modbus/TCP PCAP captures with timestamped 
attack information [7], [12]. Its scenarios include false-data injection, delayed responses, brute-force 
writes, reconnaissance, query flooding and replay-related activity. Raw PCAP data preserve 
timestamps, endpoints, traffic direction, transaction and unit identifiers, function codes, addresses, 
values and potential request–response relationships. 

=== PAGE 17 ===
 
Page 17 
Its main advantage is support for packet parsing, event ordering and transaction reconstruction. 
However, PCAP packets do not contain a directly usable three-class label. Attack logs must be 
correlated with traffic using timestamps, scenarios, targets and transaction identifiers where available. 
Packet direction and request-response position must then be verified. Manipulated requests may be 
mapped to command injections, while fabricated or manipulated replies may be mapped to response 
injections. Ambiguous matches are excluded and documented. Query flooding, reconnaissance and 
replay remain assigned to the other research components. 
 
1.3.7 Random Forest for the Proposed Component 
Random Forest combines predictions from multiple decision trees trained using bootstrapped samples 
and randomly selected feature subsets [9]. It is suitable because the proposed inputs are structured 
variables describing function codes, previous commands, addresses, read/write transitions, timing, 
permissions, pair consistency and value changes. 
The model can learn nonlinear feature interactions, support multiclass classification, use class 
weighting and generate class probabilities. Feature importance or a tree-compatible explanation 
method can identify influential contextual evidence. Nevertheless, Random Forest does not remember 
sequences automatically. Command history must first be converted into lag, sliding-window, pair and 
transition features. Therefore, the novelty is the contextual Modbus representation rather than the 
Random Forest algorithm. 
 
1.3.8 Critical Synthesis of the Literature 
The literature confirms that protocol-specific modelling is more appropriate for Modbus environments 
than relying only on generic network-flow statistics. Command-injection research establishes the 
attack categories [6], deterministic modelling demonstrates the value of sequence behavior [3], and 
supervised studies support classification using labelled SCADA data [8]. 
However, existing work does not sufficiently combine request-response reconstruction, surrounding 
command behavior, access context and value transitions in an explainable supervised representation 
that distinguishes normal, command-injection and response-injection events. Dataset compatibility, 
leakage-resistant partitioning and per-class explanation also remain insufficiently addressed. 
These findings motivate Modbus-aware parsing, chronological event preservation, request-response 
reconstruction, contextual feature engineering, three-class classification, an isolated-event Random 
Forest baseline, feature-group ablation, scenario- or time-based data splits and per-class evaluation. 
 
1.3.9 Existing Systems and Products 
Snort Modbus Preprocessor 
Snort decodes Modbus traffic and allows rules to examine function codes, unit identifiers and message 
data. It also alerts incorrect lengths, non-zero protocol identifiers and reserved function codes [13]. Its 
protocol-aware rules provide fast detection of known conditions, including operations from 

=== PAGE 18 ===
 
Page 18 
unauthorized hosts. However, a valid-looking injected message may not match a predefined rule, and 
Snort does not inherently learn contextual relationships from labelled injection data. 
Suricata 
Suricata provides Modbus-aware application-layer rule keywords for protocol decoding and signature 
detection [14]. It integrates with wider network-monitoring environments, but performance depends on 
analyst-defined rules and selected fields. It does not independently provide three-class context-aware 
Random Forest classification. 
Nozomi Networks Guardian 
Guardian provides OT asset discovery, network visualization, continuous monitoring and anomaly-
based detection. It builds a behavioral baseline to identify suspicious communication, unwanted 
operations and unusual process values [15]. Its strengths include broad visibility and operational 
dashboards. However, public documentation does not disclose enough features, training-data or per-
class performance detail to reproduce command/response-injection detection academically. 
Claroty Continuous Threat Detection 
Claroty CTD provides asset inventory, behavioral profiling and multiple threat-detection engines. It 
profiles assets, communication and processes and produces contextualized alert timelines [16]. 
Although suitable for industrial security teams, its detailed Modbus injection features, model 
configuration and reproducible class-level results are not publicly exposed. 
 
1.3.10 Limitations Addressed by the Proposed Component 
The proposed component does not attempt to replace full commercial OT-security platforms. Instead, 
it addresses a specific and experimentally measurable limitation: detecting protocol-valid command 
and response manipulation using reproducible contextual evidence. 
It will address limitations in existing research and systems by: 
• Reconstructing requests and responses where transaction information permits. 
• Preserving chronological command order. 
• Separating command injection and response injection. 
• Combining protocol, access, timing, pair-consistency and value context. 
• Comparing the context-aware model with an isolated-event Random Forest. 
• Removing feature groups through ablation tests to measure their contributions. 
• Using capture-, scenario- or time-based splits to reduce data leakage. 
• Reporting per-class recall, macro F1, false-positive rate and latency. 
• Providing a class probability and short explanation for each completed prediction. 
• Publishing the feature definitions, label mapping and experimental procedure for 
reproducibility.

The specific novelty is therefore not the use of Random Forest alone. It is the construction and 
validation of an explainable, context-aware Modbus event representation for distinguishing normal 
communication, command injection and response injection. 
 
1.4 Research Gap 
Existing studies demonstrate that Modbus-specific fields and communication patterns are useful for 
identifying abnormal industrial-control traffic. Gao et al. examined command and response injection 
attacks and established their importance in SCADA security [6]. Goldenberg and Wool modelled 
expected Modbus/TCP communication sequences using a deterministic approach [3], while Beaver et 
al. evaluated supervised machine-learning algorithms using structured SCADA traffic features [8]. 
Existing systems such as Snort and Suricata also inspect Modbus fields using predefined rules [13], 
[14], whereas commercial platforms such as Nozomi Guardian and Claroty CTD provide behavioral 
monitoring and contextual alerts [15], [16]. 
However, the existing approaches remain inadequate for this individual research problem. Signature-
based systems mainly identify known function codes, malformed messages or predefined conditions. 
Deterministic sequence models can become dependent on previously observed communication 
patterns. General machine-learning methods commonly analyze individual records or generic network 
characteristics without explicitly representing the relationship between a request, its response and the 
surrounding commands. Commercial platforms do not publicly disclose sufficiently detailed datasets, 
feature definitions, model configurations or per-class results to support reproducible evaluation of 
command and response injection detection. 
Consequently, it remains insufficiently investigated whether combining the following information can 
reliably separate normal Modbus/TCP communication from command and response injection: 
• Current and previous command relationships 
• Request-response consistency 
• Source and destination roles 
• Permitted function and register access 
• Command timing and frequency 
• Register-value transitions 
• Recent read/write behavior 
Another limitation concerns dataset preparation. CICModbusDataset2023 provides raw PCAP captures 
and attack logs, but false-data-injection records cannot automatically be treated as command or 
response injection. The traffic direction and request-response position must be verified before 
assigning one of these labels. In contrast, the MSU Gas Pipeline dataset contains explicit command- 
and response-injection categories but does not provide every transaction field required for complete 
request-response reconstruction. Therefore, a reproducible label-mapping and common-feature strategy 
across these datasets has not been sufficiently evaluated. 
The proposed research addresses this gap by reconstructing Modbus request-response events where the 
source data permits, preserving command order and transforming protocol semantics and surrounding

communication into structured contextual features. A supervised Random Forest will classify each 
supported event as normal, command injection or response injection. The same classifier using only 
isolated-event features will be implemented as the baseline, allowing the contribution of contextual 
information to be measured independently of the selected algorithm.

2. OBJECTIVES 
 
2.1 Main Objective 
To design, implement and evaluate a context-aware supervised machine-learning component that uses 
Modbus/TCP protocol semantics and surrounding command context to classify supported events as 
normal, command injection or response injection. 
 
2.2 Specific Objectives 
1. To critically review existing Modbus/TCP injection-detection methods, datasets, protocol-
semantic features and evaluation practices to establish the technical requirements and research 
gaps. 
2. To prepare labelled and chronologically ordered Modbus/TCP data using 
CICModbusDataset2023 as the primary dataset and reconstruct request–response events where 
the necessary transaction information is available. 
3. To design and implement a reproducible contextual feature set that represents command 
ordering, device roles, permitted register access, timing behavior, request–response consistency 
and value transitions. 
4. To develop and tune a context-aware Random Forest classifier and an isolated-event Random 
Forest baseline for classifying events as normal, command injection or response injection. 
5. To evaluate the proposed model using leakage-resistant scenario-, capture- or time-based data 
partitions, macro precision, macro recall, macro F1-score, per-class recall, false-positive rate, 
ROC-AUC, confusion matrices, inference latency and contextual-feature ablation tests. 
6. To integrate the predicted class, confidence score and contextual explanation with the shared 
Modbus attack-detection framework using an agreed event schema. 
These objectives are measurable because they produce defined outputs: a literature review, prepared 
dataset, contextual feature set, two Random Forest configurations, experimental evaluation results and 
an integrated detection component.

3. RESEARCH DESIGN AND METHODOLOGY 
3.1 Research Design 
The study follows a quantitative, experimental design with iterative prototype development. A 
supervised multiclass classifier is appropriate because the selected datasets include attack labels and

3.3.1 Feature Construction 
Each model row will represent the current event at time t. Fixed-size context will be generated from 
the previous K events within the same session, device pair, or valid dataset grouping. Candidate 
window sizes of 3, 5, and 10 will be tuned using training and validation data. Lag variables may 
include previous function codes, addresses, command-response indicators, and time differences. 
Rolling variables may include write count, response count, distinct-address count, invalid-transition 
count, average inter-arrival time, and maximum absolute value change. 
The primary CIC feature profile will use available transaction IDs, unit IDs, source/destination roles, 
function codes, addresses, values, directions, timestamps, pair-consistency indicators, response delay, 
exception flags, and previous-event windows. The secondary MSU profile will use its command-
response indicator, chronology, function, address, process variables, CRC rate, and time. External 
validation will use only the common features available and semantically equivalent in both sources. 
 
3.3.2 Prevention of Target Leakage 
CIC attack names, attack-log labels, folder names, capture filenames, scenario identifiers that directly 
reveal the attack, and post-event annotations will never be supplied as model inputs. They are used 
only to construct or audit labels and grouped partitions. The MSU binary result, categorized result, and 
specific result fields are also labels and will not be used as features. Rolling windows will not cross 
scenario, session, capture, training, validation, or test boundaries. 
 
3.4 Model Selection: Why Random Forest? 
Random Forest is selected because the engineered features are predominantly structured tabular 
variables, the available labelled data are moderate in size, and decision-tree ensembles learn nonlinear 
interactions without the data and computing demands of deep sequence models. It is robust to mixed 
feature scales, supports class weighting, provides feature-importance information, and can produce 
class probabilities for confidence scoring. Context is not learned automatically: it is explicitly encoded 
through lag, window, pair, timing, permission, and value-transition features. Hyperparameters will be 
selected through training-only cross-validation.

3.4.1 How Random Forest Works in Command and Response Injection Detection in 
Modbus/TCP Using Context-Aware Command Analysis 
Random Forest trains many decision trees on bootstrapped samples of the training records. At each 
node, a tree evaluates a random subset of features, reducing correlation among trees. The forest 
combines class votes or average probabilities. One tree may use a write-function indicator and 
abnormal value change, while another may use an unusual address transition and short response delay. 
The ensemble can therefore learn nonlinear combinations of contextual evidence. Random Forest does 
not remember sequences automatically; lag, window, pair, timing, permission, and value-transition 
variables must first convert context into a fixed feature vector.

3.5.2 Evaluation Interpretation 
Macro precision, recall, and F1 give equal importance to all three classes. Per-class recall will show 
whether either injection type is missing. The false-positive rate matters because excessive alerts reduce 
operator trust. ROC-AUC and precision-recall AUC will supplement threshold-dependent metrics. 
Detection latency will be measured on documented hardware. Where feasible, grouped bootstrap 
confidence intervals will quantify uncertainty. 
Success will be assessed comparatively rather than through an unsupported accuracy promise. The 
proposed model should improve macro F1 and injection recall over the baseline without an 
unacceptable increase in false positives or latency. Statistical significance and practical effect size will 
both be considered. 
 
3.5.3 Explainability and Error Analysis 
Global permutation importance will identify influential feature groups. A local tree-compatible method 
such as SHAP may be used if its output is stable and computationally practical. Each alert should show 
the predicted class, probability, current function and address, and a small number of contextual 
reasons. False positives and false negatives will be reviewed by class, scenario, function code, address 
range, and window size to identify label problems, missing context, distribution shift, or model 
limitations.

Only public datasets, authorized laboratory traffic, and non-production devices will be used. Raw

class imbalance, missing data, false positives, and dataset limitations to avoid overstating safety or 
real-world generalization.

frameworks such as scikit-learn and PyTorch where required. This reduces the requirement for 
specialized computing hardware. 
• Software Tools: Python, pandas, NumPy, scikit-learn, Wireshark, TShark, Scapy, PyShark, 
and other required open-source technologies may be used during development. Therefore, the 
prototype is not expected to require significant software-licensing costs. 
• Ongoing Maintenance and Patch Releases: Operational costs may include maintaining a 
secure software repository, distributing software updates, correcting dependency 
vulnerabilities, maintaining protocol parsers, and updating the dashboard. 
• Support and Baseline Calibration: Engineering time may be required during customer 
onboarding to collect normal traffic, configure the system, establish operational baselines, and 
tune component-specific thresholds. 
• Documentation and Compliance Packaging: Costs may arise from preparing and maintaining 
user manuals, installation instructions, integration guides, model documentation, release notes, 
and security-verification records. 
• Deployment and Integration: Additional costs may depend on the customer’s network 
architecture, number of monitored sites, hardware availability, integration requirements, and 
support level.

6.6 Maintenance, Versioning, and Patch Updates 
To maintain detection accuracy and system stability in continuous industrial environments, the 
following maintenance lifecycle is proposed: 
• Periodic Version Releases: Major software versions may be released annually to introduce 
improved detection models, enhanced integration capabilities, additional reporting functions, 
and updated dashboard features. 
• Routine Security and Patch Updates: Maintenance releases may be provided every two 
months or when required to deliver parser improvements, dependency-security patches, 
software corrections, and interface refinements. 
• Baseline Recalibration and Model-Drift Maintenance: Recalibration may be required when 
a plant updates PLC firmware, introduces new PLCs or RTUs, changes register mappings, 
modifies device roles, or changes normal polling intervals. 
• Model Version Control: Each deployed model should have a recorded model version, 
preprocessing version, feature-set version, training date, and supported input schema. 
• Staged Deployment: Software and model updates should be evaluated in a testing or staging 
environment before operational deployment. A rollback option should be available if the update 
causes unexpected behavior. 
• Passive and Non-Disruptive Operation: Updates should be deployed using a controlled 
process designed to minimize disruption to SCADA monitoring and industrial operations. 
• Containerized Deployment: Container technologies such as Docker may be evaluated to 
isolate individual components, manage dependencies, and simplify version updates. Their 
suitability will be confirmed during prototype integration testing.

6.7 Competitive Advantage 
• Comprehensive Multi-Attack Coverage: The framework integrates specialized components 
for detecting denial-of-service, reconnaissance, command and response injection, and replay 
attacks. 
• Protocol-Aware Analysis: It analyses relevant Modbus/TCP information such as MBAP 
header fields, function codes, register addresses, transaction relationships, command sequences, 
timing patterns, and value changes instead of depending only on generic network-flow 
statistics. 
• Specialized Detection Components: Each attack category is processed using an analytical 
method suited to its behavior rather than using one generic detector for every attack. 
• Decision Fusion and Alert Correlation: Outputs from the four components are combined to 
provide a unified classification, confidence score, and incident explanation. 
• Low Computational Requirements: The framework is intended to operate on lightweight 
industrial computers, edge servers, or virtual machines without requiring expensive specialized 
hardware. 
• Passive Deployment: The solution monitors copied network traffic and does not require 
modification of PLC logic or active interference with the control process. 
• Root-Cause Explainability: Each alert can identify the evidence contributing to the decision, 
such as a traffic-rate increase, abnormal scanning sequence, unauthorized register access, 
inconsistent response, abnormal value transition, or duplicated transaction pattern. 
• Modular Design: Each detection component can be maintained or updated separately while 
continuing to communicate through a shared result and integration format. 
• Academic Transparency: Unlike proprietary systems, the research prototype documents its 
selected features, models, evaluation methods, assumptions, and limitations. 
Any claimed improvements in accuracy, recall, detection latency, or false-positive rate will be 
supported by experimental results before being presented as verified commercial advantages.

intellectual-property policies. Ownership of the algorithms, protocol-parsing code, trained model files, 
contextual features, fusion logic, dashboard, diagrams, and documentation must be confirmed with the 
university, supervisors, and research-team members before commercialization.

product.
